## 严重：会导致错误行为

> **更正（2026-10-13，审计后复核）**：原先列为 #1、#2 的"令牌 off-by-one"经**端到端往返**复核后**不成立为可见缺陷**——存储侧与解析侧两处不符合 1-based 约定的写法**互相抵消**，净结果正确（推导见文末「已撤回的结论」）。它们仍然是不符合 API 约定的**隐患**：只修一侧必然弄坏功能。真正残留的缺陷只有"指向第 1 页的链接不存令牌"这一条（见 #1 的"残留"段）。
>
> 同理，#3、#4 两条"HIGH"目前只是**逐行分析**的结论，尚未做端到端验证（页面项几何用的是裁剪框还是媒体框、显示朝向用的是用户旋转还是总旋转，我还没读完那条链），**在复核之前不得当作事实**。

### 1. 令牌存储与解析都不符合 1-based 约定（隐患，非可见缺陷）+ 第 1 页残留缺陷

`generators/poppler/generator_pdf.cpp:550`（存储）与 `:510-515`（解析）

- `Catalog::getPageRef(int i)` 是 **1-based**：`if (i < 1) return nullptr;` … `return &pages[i - 1].second;`（`external/poppler/poppler/Catalog.cc:201-214`）
- `Poppler::LinkDestination::pageNumber()` 是 **1-based**（`Link.cc:233` `pageNum = obj0.getInt() + 1`；`qt6/src/poppler-link.cc:272` 原样拷贝，`:290` 用 `doc->getPage(pageNum)` 也按 1-based）
- 既有代码把它转成 0-based：`viewport.pageNumber = destination.pageNumber() - 1`（`generator_pdf.cpp:223`）

**净结果**：存储用 `getPageRef(0-based)` 取到"前一页"的对象（k≥2 时是 0-based 第 k−2 页），解析循环又用 1-based 语义返回 `page`，于是返回 `k−1` —— 恰是目标页的 0-based 索引 ✓。**用户可见行为正确**，实测也证明确实正确。

**残留缺陷（真实）**：目标为**第 1 页**时 `getPageRef(0)` 返回 `nullptr` → 不存令牌、`viewport.pageNumber` 保持 0 未被置为 −1 → 在前方插入页面后，该链接仍会指向错误页码（本次要修的旧毛病在这一个 case 上原样保留）。

**隐患**：两处约定错误互相抵消，**只修一侧必然破坏功能**。若要修正，必须同时：存储 `getPageRef(viewport.pageNumber + 1)`，解析改 `for (int page = 1; page <= getNumPages(); ++page) … return page - 1;`（并把循环延伸到最后一页）。修正后才能让第 1 页的目标也拿到令牌，从而彻底消除页码缓存残留。

### 2. 「令牌解析看不到最后一页」的影响在现状下不成立

`generator_pdf.cpp:510` 的循环确实只覆盖 1..n−1，但因为存储侧同样偏了一位，**存进去的令牌永远不会指向最后一页**，所以这个洞目前不会被触发。只有在按 #1 修正存储侧时才会变成真问题——这也是必须两侧同时修、且循环必须延伸到 `<= getNumPages()` 的原因。

### 3. 页面尺寸拖拽的旋转映射（HIGH，**待端到端复核**）

`part/pageview.cpp:5642` 传的是 `page->rotation()`（用户旋转），而 `totalOrientation()` 才是含文档 `/Rotate` 的总旋转（`core/page.h:81-92`、`core/page.cpp:184-196`）；`core/document.cpp:3837` 同样只按用户旋转交换宽高。
**待验证**：页面项的显示几何与坐标换算究竟用的是哪一个（若整条链都统一用用户旋转，则本条的"错边"结论不成立）。复核前不作为事实。

### 4. 手柄画在媒体框、增量基于裁剪框（HIGH，**待端到端复核**）

`part/pageview.cpp:344-347` 的 `pageSizePageRect` 走 `pdfLinkContentRect` → `uncroppedGeometry()`（`:216-225`），而 `pageSizeDisplayDeltaInPoints`（`:1393-1400`）的换算按裁剪框。
**待验证**：本应用里"可见纸张"到底是 `croppedGeometry()` 还是 `uncroppedGeometry()`。链接手柄用的是同一个 `pdfLinkContentRect` 且用户认可其位置正确，这**与该条结论存在张力**，必须先读清页面项几何再定性。

## 中等：行为不一致或状态残留

### 5. `movePage` 仍在清空所有链接框（已复核）

`core/document.cpp:6616-6625`（`renumberPages()`）

```cpp
page->setObjectRects({});
```

这是**第二处**清空点，我上次只改了 `publishPageTopologyChange()`。触发：在页面管理里拖动重排页面（`part/part.cpp:4640`）。
后果：高亮短暂消失、发出的 `DocumentChanged` 让 PageView 丢掉选中的链接（`part/pageview.cpp:2911-2913`）；下次渲染会自愈（`resetPageTopologyCaches` 复位 `rectsGenerated`）。
**修法**：删掉这句。

### 6. 改名后仍有「持有旧名字」的东西（已复核）

`generators/poppler/generator_pdf.cpp:3865-3876` 的 `renameNamedDestination` 只重置了 `rectsGenerated`，没有置 `docSynopsisDirty`（只在 771/1034/1171/1190/1379/1528 处设置）。

- **大纲**：缓存 DOM 里存的是 `ViewportName` 旧名字（`:2823-2825`），`tocmodel.cpp:150-155` 通过 `metaData("NamedViewport", 旧名字)` 解析 → 改名后解析失败、条目点了没反应
- **页面打开/关闭动作**（`:983-990`）与**文档附加动作**（`:917-921`）里的 `GotoAction` 同样保留旧名字，从不刷新

**修法**：改名时置 `docSynopsisDirty` 并通知目录/目标列表；同时重建页面与文档级动作（或在解析处对旧名字做一次回退尝试）。

### 7. 拖拽没有取消路径（页面尺寸）

`part/pageview.cpp:4311-4377` 的 Escape 分支覆盖了点击编号、阅读视图、OCR、链接、目标，**没有** `pageSizeDragging`；`4705-4753` 的拖拽分支无条件吞掉所有移动事件，即使左键已松开；没有 `leaveEvent`/窗口失活处理。
后果：若 release 事件丢失（窗口失活、抓取丢失），虚线预览与拖拽状态会一直留着，视图吞掉后续移动，直到切换模式。另外拖拽中 Ctrl+Z 会让 `pageSizeDragStartRect/Size` 变成过期几何。
**修法**：Escape 与窗口失活取消拖拽；移动事件发现左键未按下即视为取消。

### 8. 光标可能残留（页面尺寸）

`pageSizeCursorSet` 从不复位，`setPageEditModeEnabled(false)`（`pageview.cpp:1313-1334`）与手柄禁用分支（`7714-7718`）都不恢复光标；`updatePageSizeCursor` 的 else 分支（`7661-7663`）只 `unsetCursor()` viewport，而视图自身的 resize 光标在 7659 设置。
触发：页面编辑下悬停边框（出现缩放光标）→ 用快捷键/工具栏切回阅读模式（不移动鼠标）→ 光标保持斜向缩放样式。

### 9. 手柄没有按「可编辑性」把关（页面尺寸）

`part/part.cpp:4752/4988` 只判断 `m_editingMode==Pages`，而工具栏动作判断的是 `canEditPages && canChangePageSize`（`4875-4877`）。
触发：打开非 PDF／远程／压缩包文档并进入页面编辑 → 每页都出现手柄与缩放光标，一拖就是模态提示"只能在本地 PDF 文件中修改页面尺寸"。
**修法**：把同一条件传给 `setPageEditModeEnabled`。

## 复核后确认「没问题」的部分

- **页面对象号在移动/删除/插入/撤销中都不变**：`movePage` 只重排 `/Kids`（`PdfPageSequenceEditor.cc:1948-1965`），`detachPage` 只从页树摘除引用、不释放对象（`1910-1927`），`attachPageAfter` 重新挂回同一个 `Ref`（`1929-1946`）→ 令牌方案的核心前提成立；复制页得到全新 `Ref`（`1730`），不会与源令牌撞车。
- **`m_pageOrder` 不会失配**：它在各处都是恒等映射（`899-905`、`1030-1033`、`1086/1109`），页面重排改的是文件页树而非该映射 → 我先前担心的"逻辑/原生"错位目前不存在。
- **改名不会清掉链接框与选中**：改名路径不再发 `DocumentChanged`（`document.cpp:6937-6953`），PageView 唯一可达的反应是 `notifyPageChanged(Annotations)`（`3305-3337`），它在矩形仍在时保留选中（`3326-3336`），且矩形由同一套来源重建 → 逐位一致。
- **保存/重开后令牌正确**：`swapBackingFile` 从新载入的文件重新生成链接与令牌（`generator_pdf.cpp:1146-1153`）。
- **旋转增量表本身正确**：对总旋转 0/90/180/270 独立推导与实现一致；8 个手柄的种类/顺序/中心一致；撤销是"已施加（钳制后）增量"的精确取反（被固定的边增量恒为 0，钳制按轴等比缩放，锚点成立）；编辑器侧校验（面积>0、每边≤20000、NaN 拒绝、两个盒子都写、`/Rotate` 与 `/UserUnit` 不动）正确。
- **本地 PDF 守卫**在三个入口都生效（`part.cpp:7769`、`7802`，拖拽经 `1542→changePageBox`）。
- **模式互斥**正确：`syncFrame` 统一切换交叉引用/OCR/页面编辑，禁用交叉引用时会清掉链接手柄状态（`pageview.cpp:1411-1425`）；手柄命中判断先于链接/选择（`5183` vs `5225`）。
- **应用层已无遗留的直接 `destViewport()` 消费方**：全仓库只剩 `core/document.cpp:6781`，即 `gotoTarget()` 内部的第一层判断。
- **链接动作不需要序列化**：链接是 `Page::objectRects` 里的对象，每次从 PDF 重建；`Okular::Action*` 只挂在标注上（Screen/Rendition 等），与 Goto 链接不同路径 → 新加的 `pageToken` 不存在"侧车丢失"问题。

## 已撤回的结论（审计后复核）

| 原结论 | 状态 | 说明 |
|---|---|---|
| #1「令牌存的是前一页 → 点击跳早一页」 | **撤回** | 存储侧偏一位、解析侧偏一位，**互相抵消**：目标为 1-based 第 k 页（k≥2）→ 存 0-based 第 k−2 页的对象 → 解析循环返回 `k−1`，恰是目标页的 0-based 索引 ✓ |
| #1「指向第 1 页的链接不存令牌」 | **成立**（残留缺陷） | `getPageRef(0)` 返回 `nullptr`，不存令牌、页码留在 viewport；该 case 在前方插入页面后仍指向错误页码 |
| #2「最后一页永远解析不出来」 | **撤回（现状不可触发）** | 存储侧同样偏位，令牌不会指向最后一页；只有单侧修正后才会变成真问题 |
| 「`testLinkTargetFollowsPages` 在当前代码上必然失败」 | **撤回** | 该用例断言的正是 `k−1`，在当前代码上通过 |
| #3、#4（页面尺寸两条 HIGH） | **待端到端复核** | 均为逐行分析结论；页面项几何链（裁剪框/媒体框、用户旋转/总旋转）尚未读完，复核前不作事实 |

**方法教训**：这次把"每一行是否符合 API 约定"当成了结论，而没有把**完整往返**走一遍——两处相反的偏差互相抵消，逐行审查看不出来。今后凡涉及索引/坐标/基数的改动，必须做一次"从输入到最终观察"的端到端推演，并尽可能用可运行的检查去证伪。
