# Mengshee 2026.0.25.0

A functional release. It makes links that point into another document usable: they can be
re-pointed when the file they name has moved, they can be created, and their target may be a
page of that file or a named destination in it. The release also answers a link whose file is
missing, which used to do nothing at all.

## Links that point into another document

A PDF can carry a link to a page of another file (`/GoToR`). Mengshee's own editors never made
one, but the viewer has always followed them - and 2026.0.24.0 broke that, which 2026.0.24.1
restored. This release makes them first-class:

- **Re-pointing.** Edit Link Destination… is now offered for such a link, with the file name and
  page it stores, and **Locate File…** to name the file again. This is the case that was
  impossible before: a main paper links to its Supplementary Information, a submission system
  renames the SI, and there was no way to fix the link in the application.
- **Creating.** The link editor offers **File in another document** for a new link as well, with
  either a **page** of that file or a **named destination** in it.
- **How it is written.** A named destination is stored as the plain name, which survives
  repagination of the other file; a page is stored as the zero-based page number the format uses
  for a cross-file destination (a page reference would be wrong: it can only mean a page of this
  document). The name is never resolved against this document, only against the file it belongs to.
- **Saying what a link points at.** Hovering one now shows `Opens target.pdf at page 3` instead
  of the generic "Open external file", in the page view and in presentation mode. When the file
  it names is not there, the document says so (`Could not open "target.pdf": the file was not
  found.`) instead of appearing to do nothing.
- **Deleting one and undoing** keeps it a cross-file link rather than turning it into an internal
  one.

The dialog marks this kind as **not recommended** with a warning icon beside it and a short
tooltip: the format stores only the other file's name, so renaming or moving that file breaks
the link, and merging the documents and using internal links is the more robust option. The
application supports it anyway. [How link targets resolve](../link-targets.md) explains it.

## Also in this release

- Two dialog bugs found while making the above testable: a radio button cannot be unchecked with
  `setChecked(false)` in an auto-exclusive group (and disabling the checked one unchecks it), so
  the page/name choice was silently read as the other; and `QDialogButtonBox` disables itself
  after the window is shown when it has no default button, which left Ok dead.
- `docs/repro/2026.0.24.1.md` describes how to see each behaviour that release fixed on
  2026.0.24.0, and how to build and run the tests here.
- `*.pdf` are exempt from line-ending conversion, because their cross-reference tables store byte
  offsets.

## Validation

- `parttest` link set: **14 passed, 0 failed**, covering the round trips (create and edit, page
  and named destination, each saved and reopened), re-pointing, the dialog's kind being offered
  only where it belongs, and the destination resolving in the *other* file.
- The whole suite: 101 passed, 10 failed, 2 skipped. The failures are the environment ones
  recorded before (this session cannot start a KIO worker, and the application's data directory
  is not deployed for the test run): OCR, text selection and copying, the note-page click,
  scrolling, and `testSaveAs`. **No link test fails.**
- The named destinations of the test fixture were verified independently with Poppler
  (`section.2` → page 2, `section.3` → page 3), as was the stored link in the source fixture.
- Not verified: the native file chooser's own interaction (it cannot be driven from a test; the
  path after it is covered), and undo of deleting a cross-file link.
