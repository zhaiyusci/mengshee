# Mengshee 2026.0.23.1

## Note pages

- Moving a note link in **Cross-References** mode keeps its label. Changing an annotation rectangle drops that annotation's appearance in the backend, because a generic appearance belongs to the rectangle it was built for; the label is this application's policy, so it is rebuilt for the rectangle the link moved to. The link, its destination and its action are untouched, and the freed appearance is replaced in the same cross-reference entry, so moving a link back and forth does not accumulate form objects.
- The label is not remembered at edit time: the destination name the link points at is read back (`mnote-<page>-<sequence>`), so a note link keeps its label when it is moved, resized, undone, redone, or recreated after its deletion — and a link that points somewhere else is left alone.
- Because the label is drawn as part of the page image, the page whose link moved is refreshed as the last thing the edit does, in the undo and redo steps as well, so the label follows the link on screen instead of staying where it was.

## Building

- The Windows build now guarantees that the trees a developer is meant to start — the installed tree and the package stage — run with the rights of a normal user, and **fails** instead of handing out a tree that would misbehave. `windows-build/scripts/make-runnable.ps1` restores the integrity label and reads it back; the pipeline runs it after deployment and before anything is packaged, and the staged smoke test checks it before launching the application.
- Rationale: Windows starts a process at the lower of the user's integrity level and the executable's label, and build output created inside a restricted (low integrity) session inherits a low label from that session. Such an application starts normally but cannot write `%TEMP%` or `%LOCALAPPDATA%`, so saving fails with `Could not open the temporary file for saving.`, KIO fails with `Could not create socket for launching a KIO worker for protocol "file".`, and per-user files are redirected to `AppData\LocalLow`. Raising a label needs a normal session, so the build cannot repair what a restricted session produced; it reports the exact `icacls` command instead. `-DALLOW_LOW_INTEGRITY=ON` records a warning for builds that relabel the trees later.

## Validation

- The label policy is covered at the level it lives at. A standalone check built against the freshly built libraries created a labelled internal link, moved it through `Document::editPdfLinkRectangle()`, and reported: the live document draws the label box (39907 px) and text (990 px) inside the new rectangle and nothing in the old one; the saved file's moved link carries `/AP <</N …>>`; the reopened file draws the same ink at the new rectangle and none at the old; the same operation without asking for the label again after the move loses it (`/AP` absent, no ink), which is the behaviour being fixed; and a never-labelled link stays clean. Destination parsing accepts `mnote-3-1` / `mnote-12-7` and rejects `mnote-3-0`, `mnote-3-`, `mnote-x-1`, `mnote-0-1`, `mnote-3-1x`, `other-3-1` and `mnote-3-1-2`.
- `parttest` covers the same operation end to end in `testAddNotePage`: after the note is created, the link is moved in cross-reference mode, and the test requires the label box and text inside the new rectangle and none in the old one, the frame showing the link to follow it, undo and redo to carry the label with the link, and the reopened saved file to draw the label at the new rectangle only — which can only come from the moved link's own `/AP`.
- Not run for this build: the `parttest` case and the packaged smoke test were not executed on the release machine, which is itself restricted: a process started there cannot write the temporary tree a GUI test needs. The document and generator layer, including the saved file, is covered by the standalone check above; the application-side part of the move (deriving the label from the destination, refreshing the page image) is what `parttest` verifies.
- Packaging: the installer was built from the staged tree after the new run-tree check, the staged `Okular6Core.dll`, `okularpart.dll` and PDF generator hash-match the freshly built ones, so it carries this change, and the installed `Setup.exe` was given the label of an ordinary process as well — without it Setup stops at once with `Error 5: Access denied` while unpacking itself into `%TEMP%`. The published copy in `output/releases/2026.0.23.1` was checked and repaired by `windows-build/scripts/make-release.ps1`, which is now the release step.
