# Reproducing what 2026.0.24.1 fixed

Each case below says what to open, what to do, what 2026.0.24.0 did, and what 2026.0.24.1
does. The two that are hard to set up by hand (a cross-file link, and the tooltip) have
fixtures or automated tests.

To see the old behaviour, install the `Mengshee-2026.0.24.0-Setup.exe` from its release page,
or build the tag `v2026.0.24.0`.

## 1. A link that points at the first page

Needs any local PDF with at least two pages.

1. Enter **Cross-References** mode. On page 2, create a link: **leave the destination name
   empty** and set the destination page to **1**.
2. Save. Click the link: it goes to page 1, which is correct so far.
3. Insert a blank page **before the first page**.
4. Click the link again.

- 2026.0.24.0: it lands on the **new blank page**. The link kept a page number instead of
  remembering the page it names.
- 2026.0.24.1: it follows the content to what is now page 2.

Automated: `parttest.exe testLinkToFirstPageFollowsInsertion` (fails on 0.24.0 with
`pageToken().isEmpty()`, passes on 0.24.1).

## 2. A link that points into another file

Mengshee does not create these links: its editors make internal links and URL links. A PDF can
carry one anyway (a `/GoToR` action, as produced by Acrobat, InDesign, and some journal and
teaching tool chains), and following it has always been supported - `openRelativeFile` opens
the named file and the destination page is applied to it. That is the behaviour this release
restores, so the fixture exists instead of a recipe.

Fixture: `autotests/data/goto-remote-source.pdf` and `goto-remote-target.pdf`. The link inside
the source names the other file as `target.pdf`, so copy both files into one directory and
rename them to `source.pdf` and `target.pdf`.

1. Open `source.pdf`.
2. Click the link on its page.

- 2026.0.24.0: `target.pdf` opens at **page 1**. The destination's page number was cleared and
  replaced by a page identity taken from the wrong document.
- 2026.0.24.1: `target.pdf` opens at **page 3**, which is what the link names.

Automated: `parttest.exe testCrossFileLinkKeepsItsPage`.

## 3. Reordering pages drops the link boxes

Needs a local PDF with links (create a few first, or use `autotests/data/pdf_with_internal_links.pdf`).

1. In **Cross-References** mode, click a link so its box is selected.
2. Switch to the **Pages** mode and drag a page to another position.
3. Look at the page again, without scrolling it out of view and back.

- 2026.0.24.0: every link box on the pages that were already rendered **disappears**, and the
  selected link is deselected. They come back only after the page is rendered again.
- 2026.0.24.1: the boxes and the selection stay.

## 4. An outline entry stops working after its destination is renamed

1. In **Cross-References** mode, put a named destination on a page.
2. Add it to the contents (**Add Current Page to Contents**), so the outline entry points at
   that name.
3. Rename the destination.
4. Click the outline entry (the contents pane, or in presentation mode).

- 2026.0.24.0: nothing happens. The outline was built with the old name and was not rebuilt.
- 2026.0.24.1: it goes to the page.

## 5. No tooltip in presentation mode

Needs a PDF with a link whose destination is an explicit page (the one from case 1 will do).

1. Open it, press **F5** to present, and hover the link.

- 2026.0.24.0: no tooltip at all, while the same link shows one in the normal view. The action
  no longer carried a page number and nothing resolved it for this view.
- 2026.0.24.1: `Go to page N`.

## Running the tests

Three things that cost time here, so they are worth knowing:

- The release pipeline configures with `-DBUILD_TESTING=OFF`, so `parttest` disappears from the
  build tree after a release build. Turn it back on with
  `cmake -S <checkout> -B <build> -DBUILD_TESTING=ON`.
- Building only `parttest` leaves the **generator plugin** stale, and the link code lives
  there, so tests can pass or fail against the wrong code. Build everything (`ninja` in the
  build directory) at least once after changing the generator.
- The freshly built `bin` directory has to come first on `PATH`, together with Qt and the
  poppler SDK, and `QT_QPA_PLATFORM_PLUGIN_PATH` has to point at Qt's `plugins/platforms`.

```powershell
$ws = "C:\Users\jairy\Documents\mengshee\windows-build-workspace"
$build = "$ws\build\mengshee-standalone"
$env:PATH = "$build\bin;$ws\sdk\bin;C:\Qt\6.11.1\msvc2022_64\bin;$env:PATH"
$env:QT_QPA_PLATFORM_PLUGIN_PATH = "C:\Qt\6.11.1\msvc2022_64\plugins\platforms"
& "$build\bin\parttest.exe" testLinkTargetFollowsPages testLinkToFirstPageFollowsInsertion testCrossFileLinkKeepsItsPage
```

The whole suite is `& "$build\bin\parttest.exe" -o report.txt,txt`. It needs a normal session:
the save and copy tests fail here with
`kf.kio.core: couldn't create worker: "Unknown protocol 'file'."` and the application's data
directory is not deployed for the run, which is why 15 of them fail in this environment and
none of the link tests do.
